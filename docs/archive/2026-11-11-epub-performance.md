# EPUB 图片密集型章节加载优化

> 历史实施记录，仅代表文中基线与当时的测量环境，不作为当前能力或后续设备验收的替代。现行阅读器行为见 [READER.md](../READER.md)。

测量基线：`a3c9fec`（`feat/epub-image-reading`），2026-11-11。主工作树 `master` 当时为 `79f79ed`；本阶段分支从 `a3c9fec` 创建，尚未合并。

## 1. 问题范围

图片集中在同一章节的 EPUB 在首次打开时要先测量整章图片、完成整章分页，之后才解码可见图片。尺寸只保存在内存且上限为 256 项，跨进程丢失；图片批次最多四项，每批重新打开 ZIP 目录。结果是冷进程打开整章图片漫画需要约 4 秒，而普通小说和按页分章漫画没有同等瓶颈。

本轮只处理插图测量、读取与缓存链路，不改正文排版、章节 ID、UTF-16 段落坐标、书签、阅读进度和原书文件。

## 2. 实现

- 导入 EPUB 时，为同一章节超过四张不同图片的章节预建常规 PNG / JPEG 尺寸；短章节和普通小说不扫描整本插图。尺寸记录源内容身份、原书大小与修改时间、媒体映射哈希，最多 1 MiB。
- 旧书首次需要尺寸时，用一个后台 ZIP 会话补建 `.image-dimensions.json`；之后跨进程复用。损坏、超限或写入失败时退回原有读取路径，不使整本导入或阅读失败。
- 分页时大章节先获取尺寸提示，并优先读取目标附近最多四张图片；短章节仍沿用单批读取。分页不再要求把整章压缩图片字节保留到界面线程。
- 内存尺寸缓存最多 256 项；压缩图片缓存从 64 MiB 调整为 32 MiB；邻页预解码保留当前页、后两屏和前一屏的有界窗口。
- 尺寸提示只用于排版，不替代显示时的 ZIP 大小、结构、CRC 与解码校验。EXIF、GIF、WebP 等继续使用平台解码器和既有失败重试。

同时移除没有调用的 Jsoup、CommonMark 和 PDFBox Android 依赖，并在按指定架构构建时同时过滤原生 CMake 与 APK 库。该项影响包体和构建，不是阅读性能收益。

## 3. 测量方法

- 设备为 x86_64、API 36 模拟器；应用使用 Profile 构建，基线包与优化包分别安装、交替顺序测量。
- 样本为普通小说、按页分章漫画、整章图片漫画和 350 MB 级大 EPUB；每条记录包含内容就绪与图片可用两个独立时间点。
- 场景覆盖冷进程打开、同进程复开、目录远跳、相邻页前后翻页；每场景 5 次有效样本，共 200 条交替配对记录。
- 图片密集章节另用“全部图片位于同一章”的大型样本补测导入与首次打开。
- 单章大样本为 350 MB、588 张图片、单条目录项的 EPUB；修正后导入确认为 1 章、588 条媒体与尺寸记录。早期 350 MB 样本的目录把每个段落拆成章节，其“单章”补测数据不能使用，已排除。
- 单章样本做 1 轮交替 A/B，共 30 条有效记录；冷进程打开含 5 次独立冷启动和前后翻页前的 2 次冷启动。
- 模拟器结果不等于 ARM64 实机结果；冷进程不等于冷系统页缓存。

## 4. 结果

以下为测试驱动记录的图片就绪中位耗时（毫秒），基线 → 优化。就绪指阅读区域内的 `RenderImage.image` 已非空，并经过帧等待；不证明最终 GPU 呈现、透明度动画完成或整屏图片全部可见。计时从驱动发起阅读操作开始，不包含应用启动及用户操作目录界面的时间：

| 场景 | 温度 | 基线 | 优化 | 变化 |
| --- | --- | ---: | ---: | ---: |
| 整章图片漫画，章节起点 | 冷进程打开 | 4016.5 | 865.7 | -78.4% |
| 整章图片漫画，远端跳转 | 冷进程打开 | 3826.0 | 747.8 | -80.5% |
| 按页分章大 EPUB，远端跳转 | 冷进程打开 | 669.8 | 633.7 | -5.4% |
| 普通小说，远端跳转 | 冷进程打开 | 997.1 | 974.7 | -2.2% |
| 按页分章漫画，远端跳转 | 冷进程打开 | 664.3 | 679.5 | +2.3% |
| 整章图片漫画，章节起点 | 热进程复开 | 386.8 | 341.7 | -11.7% |
| 普通小说，远端跳转 | 热进程复开 | 469.4 | 562.2 | +19.8% |
| 按页分章漫画，远端跳转 | 热进程复开 | 331.4 | 356.8 | +7.7% |
| 相邻页前后翻页（整章样本） | 翻页 | 405–434 | 386–413 | -9.4% 至 -4.9% |
| 相邻页前后翻页（其他样本） | 翻页 | 399–778 | 400–802 | -3.1% 至 +5.7% |

收益集中在整章图片样本的冷进程首次打开；普通小说和按页分章漫画没有实质提升，普通小说热复开实测慢 19.8%，按页分章漫画热复开慢 7.7%。每场景仅 5 次，尚不能区分回归与环境波动，不应宣称这些路径已优化或没有回归。翻页路径基本持平。

极端单章样本（350 MB、588 张图片同章）单独补测，同样为基线 → 优化：

| 场景 | 样本数 | 基线 | 优化 | 变化 |
| --- | ---: | ---: | ---: | ---: |
| 导入 | 1 | 9028 | 13341 | +47.8% |
| 独立冷进程打开 | 5 | 31132 | 676 | -97.8% |
| 冷打开（含翻页前的两次准备打开） | 7 | 30853 | 676 | -97.8% |
| 热进程复开 | 5 | 25070 | 454 | -98.2% |
| 向前翻页 | 1 | 435 | 395 | -9.2% |
| 向后翻页 | 1 | 401 | 426 | +6.4% |

按含准备打开的 7 次冷打开及 5 次热复开做线性插值，优化后样本 p95 分别约为 780 和 482 毫秒。小样本分位数只描述本组记录，不作为稳定的尾延迟承诺。基线冷打开耗时约为常规整章漫画样本的 7–8 倍，说明瓶颈随同一章节内的图片数量放大；该样本用于验证退化边界，不代表常见书籍的绝对耗时。优化版导入增加约 4.3 秒，是为 588 张图片预建尺寸索引的一次性成本。

常规样本导入耗时约 8.5–9.5 秒，基线与优化没有明显差异；极端单章样本因预建尺寸索引增加约 4.3 秒，见上表。最终单章补测原始记录同时保存了 `dumpsys meminfo`。按时间戳连接原始行与带场景标签的汇总行后，冷打开（7 次）就绪后的 PSS 中位数为 274.54 → 212.17 MiB（-22.7%），RSS 为 405.20 → 342.52 MiB（-15.5%）；热复开（5 次）PSS 为 275.48 → 215.87 MiB，RSS 为 406.29 → 346.32 MiB。这是就绪后的进程快照，不是峰值、泄漏测试或所有书籍的内存结论。原文件共 60 行，实际为 30 次操作各写原始行与汇总行，不能当作 60 个独立样本。

APK 体积方面，对照使用的 Profile 包为 81,604,947 字节，最终补测的优化 Profile 包为 71,857,387 字节（-11.9%）；Release 单架构包约 51–53 MiB。体积下降同时包含移除未使用依赖和 ABI 过滤，不能全部归因于阅读性能优化。

## 5. 旧书首次补建索引

旧书第一次需要尺寸时会先补建索引，实测约 2.0–2.2 秒；同进程建好索引后复开约 0.3–0.4 秒。不能把已建索引后的速度当作所有旧书首次打开的体验。该成本在导入后的普通阅读路径中单列，不通过删除原书、降低画质或清空数据规避。

- `flutter test --no-pub`：168 项通过；`flutter analyze lib test --no-pub --no-fatal-infos`：仅既有 info，无 warning / error。
- Release APK 已分别按 arm64-v8a 与 x86_64 构建，版本号保持 2277；包名为源码预览包名，使用本地调试签名，不是分发签名。
- 未在 ARM64 实机验收，也未覆盖 iOS、HarmonyOS 或 Release 实机运行。
- 大于 256 张图片的章节回归覆盖了尺寸缓存淘汰后不重复读取；导入新书保存尺寸字段、旧书补建、换源后重新读取均有测试。
- 单章样本配对测量 30 条有效记录、0 错误；最终测试书保留在模拟器 `files/local-books-v1/1613486192` 供后续测试，属于本机验证产物，不提交。
- 依赖移除后的应用许可登记和第三方文档已同步；历史 `assets/licenses/` 原文保留，不再注册为当前依赖。

1. 对普通小说和分章漫画热复开慢于基线的现象做受控复测，交替构建顺序并记录缓存状态；在原因明确前保留回归说明。
2. 用 ARM64 实机的相同构建模式验证首次打开、目录远跳、旧书补索引和快速连续翻页；补充峰值内存与低内存回收观察。

4. 仅在上述数据表明有必要时继续调整索引构建与取消策略；保留当前画质、阅读坐标和有界缓存，不以整本预解码换取速度。
